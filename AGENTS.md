# AGENTS.md

This file provides guidance to AI coding agents (Claude Code, Codex, GitHub Copilot) when working with code in this repository.

All three tools read this file directly, so it is the single place for shared rules. Claude Code reads `AGENTS.md` when a repository has no `CLAUDE.md`, which is the case here; if a `CLAUDE.md` is ever added, it must import this file with `@AGENTS.md` or Claude Code stops reading it.

## Overview

NSwag is an OpenAPI/Swagger toolchain for .NET, ASP.NET Core and TypeScript. It generates OpenAPI documents from ASP.NET (Core) and Web API controllers and generates C# and TypeScript clients from those documents. It ships as NuGet packages, a command line tool (NuGet tool, MSBuild targets and the `nswag` NPM package) and the NSwagStudio Windows UI. Document and code generation build on [NJsonSchema](https://github.com/RicoSuter/NJsonSchema) and Namotion.Reflection.

## Git rules

- Never include AI attribution in commit messages, PR descriptions, or GitHub comments. This covers agent names ("Claude", "Codex", "Copilot"), `Co-Authored-By` trailers, and "Generated with" footers.
- Use a Conventional-Commits-style prefix on commit subjects and pull request titles: `feat:`, `fix:`, `ci:`, `build:`, `docs:`, `test:`, `chore:`, `perf:`, `refactor:`. Older history is mixed, newer commits use the prefix.
- Pull requests are squash merged and GitHub appends the ` (#1234)` reference to the subject, so do not write it by hand.

## Build and test

- `./build.sh Compile Test` builds and tests everything (`build.cmd` on Windows). This is the same entry point CI uses.
- The build is [NUKE](https://nuke.build), implemented in `build/`. Targets and their dependencies: `Clean`, `Restore`, `Compile` (default, depends on `Restore`), `Test` (depends on `Compile`), `Pack` (depends on `Compile`), `Publish` (depends on `Pack`). `./build.sh --help` lists targets and parameters.
- The SDK is pinned in `global.json` (`10.0.100`, `rollForward: latestMinor`). `build.sh` uses the `dotnet` on `PATH` when there is one and otherwise installs the pinned version under `.nuke/temp`. Do not change `global.json` to work around a local SDK mismatch, install the pinned SDK instead.
- `Restore` runs `npm install` in `src/NSwag.Npm` and in `src/NSwag.CodeGeneration.TypeScript.Tests`, so Node.js is required. The TypeScript tests compile generated clients with the TypeScript compiler from that second install.
- `Compile` also publishes `NSwag.ConsoleCore` per target framework and copies the binaries into `src/NSwag.Npm/bin/binaries` (and, on Windows, the NSwagStudio output). Later targets and the console tests depend on those copies, so do not replace a `Compile` run with a plain `dotnet build`.
- On macOS and Linux the build uses the solution filter `src/NSwag.NoInstaller.slnf` instead of `src/NSwag.sln`. NSwagStudio, the WiX installer, the .NET Framework consoles and `NSwag.Generation.WebApi.Tests` (net462) are Windows only and are not built or tested there. CI runs Windows, Ubuntu and macOS.
- `Pack` and `Publish` only run on Windows, and `Pack` requires `--configuration Release`.
- A single test project runs directly, for example `dotnet test src/NSwag.CodeGeneration.CSharp.Tests`. Tests that invoke the CLI (`NSwag.ConsoleCore.Tests`) need a prior `./build.sh Compile`.

## Snapshot tests rewrite themselves locally

Generator output is snapshot tested with [Verify](https://github.com/VerifyTests/Verify). The snapshots are the `*.verified.*` files in the `Snapshots` folders of the test projects.

`src/NSwag.CodeGeneration.Tests/VerifyHelper.cs` and `src/NSwag.ConsoleCore.Tests/GenerateSampleSpecificationTests.cs` call `.AutoVerify(includeBuildServer: false)`. Locally this **overwrites the checked-in snapshot with the new output and the test passes anyway**; only on a build server does a mismatch fail. A green local test run is therefore not evidence that generated output is unchanged.

After running tests, check `git status` and `git diff` for modified `*.verified.*` files and review every change against the intended behavior. Committing a rewritten snapshot makes CI green regardless, so the review is the only safeguard. Never accept snapshot changes as "just test noise".

## GitHub Actions workflows are generated

`.github/workflows/pr.yml` and `.github/workflows/build.yml` are generated by NUKE from the attributes and custom steps in `build/Build.CI.GitHubActions.cs`. Never hand-edit the YAML, it is overwritten on the next generation. Change the C# and regenerate both files:

```bash
./build.sh --generate-configuration GitHubActions_pr --host GitHubActions
./build.sh --generate-configuration GitHubActions_build --host GitHubActions
```

Commit the regenerated YAML together with the C# change.

## Package versions

Package versions are managed centrally in `Directory.Packages.props` (`ManagePackageVersionsCentrally` with transitive pinning). Individual `.csproj` files reference packages without a `Version` attribute, so add or change a version there, never in a project file. Versions that differ per runtime (`Microsoft.AspNetCore.OpenApi`, `Microsoft.AspNetCore.TestHost`) live in the target-framework-conditional `ItemGroup`s of the same file.

`Directory.Build.props` holds the shared properties: `VersionPrefix` is the single source of the product version, warnings are errors (`TreatWarningsAsErrors`, with a documented `NoWarn` list), assemblies are strong-name signed and output goes to `artifacts/`.

## Per-runtime tool folders

The command line tool ships one folder per runtime: `Win` (.NET Framework, Windows only) and `Net80`, `Net90`, `Net100` for .NET 8, 9 and 10. `build/Build.cs` publishes `NSwag.ConsoleCore` for each target framework and copies the results into those folders, which then become the NPM package layout and the `tools/` layout of `NSwag.MSBuild`.

Adding a runtime touches around thirty files: the build, the runtime selection in `NSwag.Commands`, the NPM, MSBuild and NSwagStudio launchers, and the sample projects. Missing one is not a build error, it ships a tool pointing at a folder that does not exist. Find them with a case-insensitive grep for both spellings of the current runtime, `grep -rilE "net100|net10\.0" src build *.props *.json`, and update the folder list above as well.

Three sites that grep does not find: the SDK pin in `global.json`, the `setup-dotnet` version list in `build/Build.CI.GitHubActions.cs`, and the default `Runtime` of new documents in `src/NSwag.Commands/NSwagDocumentBase.cs`. The new sample projects also extend the `InlineData` matrix of `src/NSwag.ConsoleCore.Tests/GenerateSampleSpecificationTests.cs`, which produces a new set of snapshots to review.

## Repository layout

```
build/                              # NUKE build: Build.cs, Build.Pack.cs, Build.Publish.cs, Build.CI.GitHubActions.cs
src/
├── NSwag.Core[.Yaml]/              # OpenAPI document model
├── NSwag.Generation[.AspNetCore|.WebApi]/   # Document generation from controllers
├── NSwag.CodeGeneration[.CSharp|.TypeScript]/  # Client and controller generation
├── NSwag.AspNetCore/, NSwag.AspNet.*/       # Middlewares and integrations
├── NSwag.Commands/                 # Command line commands, runtimes, nswag.json documents
├── NSwag.Console*/, NSwag.ConsoleCore/      # CLI hosts (.NET Framework and .NET)
├── NSwag.MSBuild/, NSwag.ApiDescription.Client/, NSwag.Npm/   # Distribution
├── NSwagStudio*/                   # Windows UI, installer and Chocolatey package
├── NSwag.Sample.NET*/              # Sample apps used by the console tests
└── NSwag.*.Tests/                  # One test project per library
```

## Conventions

- Warnings are errors. Fix the cause rather than widening the `NoWarn` list in `Directory.Build.props`, and explain any entry that is genuinely needed.
- Most files under `src/NSwag.*` carry the NSwag copyright header comment. Match the surrounding file when adding one.
- Do not edit build output or generated content: `artifacts/`, `src/NSwag.Npm/bin/binaries`, `src/dist` and the generated workflow YAML.
- Changes that affect generated client or document output need a snapshot review as described above, not just a passing test run.

## Pull requests

- Base branch is `master`.
- Fill in [the pull request template](.github/pull_request_template.md). `gh pr create --body-file` bypasses it, so read the file and write the body from it rather than waiting to be shown it. Keep the Breaking changes and Verification sections, state "None" explicitly when there are no breaking changes, and record which builds and tests were actually run.
- Contributions are covered by the CLA in [CONTRIBUTING.md](CONTRIBUTING.md).
